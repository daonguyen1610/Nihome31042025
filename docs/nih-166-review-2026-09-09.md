Procurement prepares an RFQ from selected approved VND BOQ lines and quantities,
records invited vendors' immutable quote revisions and starts evaluation. BGD or
an explicitly granted award role chooses one complete quotation. Award creates a
Draft Downstream Supply/Subcontract contract in the same project/customer with
the selected vendor, quantities and prices. Signing and manual payable processing
continue through existing contract/finance workflows. Lowest-price highlighting
supports the decision; it does not select a vendor.

The independent agent reviewed production and test source without editing those
files. It used the Senior Business Analyst skill before Functional QA review.
Executing agents own test execution and browser inspection; results supplied by
them are attributed below. This reviewer owns this document only.

### Relational concurrency findings

- **FIND-03 — High, RFQ create/mutation overlap:** SQL graphs
  `/tmp/nih166-deadlock-2.xml` and `/tmp/nih166-latest-deadlock-2.xml` identify
  shared child-range conversion and opposite child lock acquisition order:
  EF creation inserts events before invitations while existing RFQ mutation
  loads invitations before events. Mutable owned collections now use update
  locks in a fixed order. A transaction-owned SQL application lock is acquired
  before transactional reads: creation takes Exclusive; all other RFQ mutations,
  including overdue work, take Shared. Creation therefore cannot overlap another
  creation/mutation in the database, while existing mutations can still run in
  parallel subject to root/child locks. Scope, token checks, Serializable isolation
  and normal GET loading remain unchanged.
- **FIND-04 — High, BOQ/procurement/payment sequence allocation:** SQL graphs
  `/tmp/nih166-deadlock-1.xml`, `/tmp/nih166-boq-deadlock-1.xml` and
  `/tmp/nih166-latest-deadlock-1.xml` identify shared-range-to-insert conversion
  during receipt codes, BOQ revision numbers and payment request codes.
  `CreateBoqRevisionAsync`, `AllocateCodeAsync` (MR/WR/WI) and
  `AllocatePaymentCodeAsync` (PAY) request update locks before reading their
  sequence range. Allocation/insertion stays within the existing Serializable
  transaction, including warehouse reversal creation. Numbering and validation
  remain unchanged; Accounting Correction (AC) allocation is outside this change.

- **FIND-05 — High, warehouse ledger read/write overlap:** graphs
  `/tmp/nih166-warehouse-deadlock-0.xml` and
  `/tmp/nih166-warehouse-deadlock-1.xml` identify ledger list/post contention
  distinct from sequence allocation. All eight receipt/issue create, update,
  post and reverse entry points acquire a transaction-owned Exclusive
  `warehouse:ledger-mutation` gate before validation reads. Draft updates now
  participate in explicit transactions. Warehouse list uses ReadCommitted when
  no transaction already exists; existing transactional callers are preserved.
  Stock, scope, posting and reversal rules remain unchanged. The deliberate
  cost is serializing warehouse writes across projects, with a 15-second busy
  conflict on lock timeout. This does not serialize all procurement operations.
  Generic detail reads were not changed without evidence of a failure there.

The reviewer inspected the source and graph resources. Update locks address the
observed shared-range conversion; transaction-owned application locks release on
commit/rollback. Negative application-lock results are checked and the transaction
is disposed before returning a retryable conflict. These mechanisms align with
[Microsoft's locking guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17)
and [sp_getapplock documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql?view=sql-server-ver17).

The deliberate tradeoff is database-wide serialization of RFQ creation against
RFQ writes. Existing-record mutations share the gate, but long transactions can
delay creation or return a conflict after the 15-second application-lock timeout.
No general deadlock-freedom or throughput claim is made.

`tools/qa/rfq_concurrency.py` is an opt-in HTTP probe for an isolated SQL-backed
stack. It creates retained evidence and reads credentials from a private file
without logging secrets. The expanded probe starts four parallel creations and
overlaps their issue with another creation, then revises/evaluates/awards all five:
three rounds cover 15 RFQs. It checks 200/409 competing same-RFQ awards, two live
and snapshot bids, five pre-award snapshot events, one award event and distinct
non-null contracts. It does not verify selected-bid snapshot field values. Final
execution passed: `/tmp/nih166-sql-concurrency-verified.log` independently shows
three rounds of five RFQs, each with a 200/409 competing award and distinct
contracts (15 total). The executing agent confirms exit zero.

Red integration logs `/tmp/nih166-integrity-red.log` and
`/tmp/nih166-line-integrity-red.log` independently inspected by the reviewer each
showed one failed partition because the invalid mutation returned success before
the guard. The implementing agents report focused 51 integration cases passed
after the corrections. The browser reviewer reports reproduction of the inactive
highlight before correction; the final targeted vendor browser log records one passing case.

These changes do not make ordinary unawarded contracts immutable. Dedicated
contract transitions and existing VO rules remain separate. No schema migration
or role grant change is required. Vendor `isActive` is an additive response field;
backend and frontend must be deployed together for the corrected highlight.

## Limits and follow-up

- InMemory integration tests do not prove SQL locks or transaction rollback. The
  new SQL probe proves its stated parallel RFQ partitions only. Same-stock
  receipt/issue/reversal races and current fault-injected rollback remain
  separate checks; prior rollback evidence is historical. Update locks may also
  serialize writers sharing index gaps, so this is not a throughput benchmark.
- Live Google Drive requires protected OAuth credentials and RootFolderId;
  metadata/scope tests do not establish external upload/download operation.
- Vendor portal/email, split award, weighted scores, MR reservation/linkage,
  currency conversion, automatic receipt/acceptance-to-payable matching and an
  actual payment ledger remain outside the approved RFQ MVP.
- The prior full-project matrices retain broader joined-workflow gaps. This RFQ
  review does not claim all possible project or business scenarios are covered.
